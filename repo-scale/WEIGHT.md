## 二 · 器械说明

### 它测什么

测的是 `git/trees` 接口给出的**工作树**，也就是你把某个提交检出到磁盘会得到的字节数。
接口里每个 blob 条目都带真实 `size`，把它们加起来就是答案 —— 不需要 blob 内容，也不需要打包。

这个数**不等于**仓库占多少磁盘：本体还要装下整个历史。两者都报，并且明确区分，
因为本报告最核心的那个事实，正藏在两者的区别里。

### 为什么是精确的，不是抽样的

`GET /git/trees/{sha}?recursive=1` 会在 **100,000 个条目或 7 MB** 处被 GitHub 截断，
并在响应里放一个 `truncated: true`。

被截断时，`weigh.py` **不猜**：它改问这一棵树的直接子项，再对每个子树重问一遍，
如此递归。每一次答案都是真实条目相加，只是请求数变多。

唯一的例外：**某一个目录自己的直接列表也被截断**。那种情况下没有更细的粒度可以问，
工具会把结果标成 `inexact` 并打印警告，而不是安静地报一个偏小的数。
本次体检中 `inexact_trees = 0`。

### 为什么时间序列跑得起

聚合值按**子树 SHA**缓存。git 树是内容寻址的 DAG：目录内容没变，SHA 就没变。
所以第二次测量只会重下真正变过的那些目录。

实测：

| | API 调用 | 耗时 |
| --- | --- | --- |
| 冷启动（第一次） | 332 | 87.6 s |
| 热启动（同一提交，缓存命中） | **3** | **3.1 s** |
| 15 个历史时间点（含两端的大目录） | 409 | 约 5 分钟 |

没有这个缓存，"给一周的历史逐点称重"是不可能做的事。

其他两条工程细节，都是被这个仓库逼出来的：

- **并行 BFS。** 冷启动是几百次往返，串行跑是半小时。改成每层并发（默认 8 路）之后是分钟级。
  用 BFS 而不是递归并行，是为了让 worker 永远不等待自己排的队。
- **失败也要落盘。** 第一次跑的时候，一个 7 MB 的响应在传输中途被重置，异常把整个进程带走了，
  几分钟的工作全丢。现在缓存每 250 条落一次盘，并且 `finally` 里无条件再存一遍。

## 三 · 一次调用会说谎

这是做这个工具的直接原因，也是最好的一课。

对同一个提交，**同一个接口**，两种问法：

```
$ curl -s ".../git/trees/main?recursive=1"        # 只看第一页
truncated: true
entries: 47,867        working tree: 4.79 GiB      files: 44,268

$ python3 weigh.py KrisTHL181/Break-This-Repo     # 处理截断
working tree: 25.45 GiB   files: 576,155   dirs: 81,943
```

**差 5.3 倍。**

第一次问法没有任何错误：响应里那个 `truncated: true` 是真的，44,268 个条目也都是真的。
它只是没告诉你还有 531,887 个文件没出现在回复里。

本报告后面所有的数字，都是第二种问法的结果。

## 六 · 账本：战争净产出 +1.95 GiB

复原是怎么做到的？看那个提交的父提交就够了：

```
$ gh api repos/.../commits/20fafdb9 --jq '.parents[].sha'
0d1f3a11…      ← 被清空到 23 个文件的那个状态
14ed270f…      ← 大破之前的那个提交
```

**它是把大破之前的提交 merge 回来的。**

而这笔账可以精确到字节：

```
开战前  (14ed270f)  25,227,666,153 B
清剩    (0d1f3a11)   2,097,173,523 B
                    ─────────────────
相加                27,324,839,676 B
复原后  (20fafdb9)  27,324,839,676 B   ← 精确相等
```

两条路径没有重叠，所以合并就是相加，一分不差。

于是这一周的总账是：

> 大破 30 连删掉了 **508,721 个文件 / 25,201,215,885 字节**。
> 13 小时后，仓库回到 **27,324,839,755 字节** ——
> 比开战前的 **25,227,666,153** 多了 **2,097,173,602 字节**。
>
> 而这 2,097,173,602 字节，正好等于**从这场战争里活下来的那 2,097,173,523 字节垃圾**，
> 加上 PR #739 那 79 字节。
>
> **战争净产出：+1.95 GiB。**

## 七 · 三条物理

不是道德判断，是可验证的机械事实。三条都直接解释了账本。

### 一、删除只移动指针，不释放重量

git 里没有「删除」这个操作，只有「当前这棵树不再指向它」。
blob 一旦进入历史就一直可达，除非重写历史。

所以那 508,721 个文件的消失**是可逆的** ——
而它之所以可逆，正是因为它在重量上是无效的。
一次 13 小时后就完整复原的删除，对仓库本体的贡献是零。

**这不是"git 很顽固"，这是"删除"在这个系统里的字面意思。**

### 二、随机数是最贵的文件类型

`000.RANDOM.FILES/` 和 `Break-This-Repo/RND100M/` 各 20 个文件，
每个 **104,857,600 字节** —— 正好是 **100 MiB**，GitHub 单文件硬上限的精确值。

这 40 个 blob 的 SHA 互不相同（核对过），所以 pack 实打实背了 **3.91 GiB**。
它们占工作树的 **15.35%**。

pack 对文本很宽容：576,155 个文件、2,347 行 C 代码、208,041 个 Rust 文件，
压完之后整个仓库本体只有 15.09 GiB，比工作树的 25.45 GiB 还小。
但在随机数上，压缩率是 1.0000。

> **想给这个仓库增重，写代码是最慢的方式。**
> 20 个 PR 合并起来的代码，不如两个 `dd` 出来的文件重。

### 三、在现有玩法下，本体只能增不能减

`main` 没有分支保护（`GET /branches/main/protection` 返回 404），
但这个仓库唯一的变更入口是**自动合并 PR**，而一次合并只能新增提交。

要把 `size` 真正降下来，只有重写历史一条路。那条路不能被表达成一个 PR。
所以只要这个玩法不变，**这个数字只会往上走**，无论往里面塞什么、删什么。

顺带一提，GitHub 自己的口径是：仓库理想 <1 GiB，**强烈建议 <5 GiB**；
单文件超过 50 MiB 会给警告，超过 100 MiB 直接拒绝。
现在的 15.09 GiB 是"强烈建议上限"的 3 倍，而且仍在增长。

## 八 · 附带发现

- **87 个子模块**（`.gitmodules`，全在 `worktree/` 下）。它们在工作树里是 gitlink，
  不占字节，但 checkout 时要拉 87 个外部仓库。工具把它们单独计数（本次 4 个）。
- **仓库里的仓库**：根目录有个 `Break-This-Repo/`，里面有 `.github/`、`README.md`、
  `rust rewrite.rs` 和 `RND100M/`。在"清理垃圾"那个时刻，它的内容就是整个仓库的全部内容。
- **进口的整段历史**：`dotnet/` 和 `FFmpeg/` 是以 `Add '<dir>/' from commit '<sha>'` 的
  方式整体搬进来的 —— 带来的是别人的目录，还有别人的提交历史。
- **合并率 96.6%**：699 个 PR，675 个已合并，1 个还开着，24 个被关闭未合并。
  在最近 24 小时里合并了 50 个。
- **最大单一文件 = 最大允许值**。这个仓库里没有一个文件超过 100 MiB —— 
  但正好有 40 个等于 100 MiB。有人量过那条线。

## 九 · 医嘱

以下为描述，不是处方。没有任何一条在建议对共享仓库做 force push —— 
那会打断 164 个 fork 和所有人的本地副本。

如果哪天真的想让本体变小，按有效性排序只有三条路：

1. **重写历史**（`git filter-repo` 去掉那 3.91 GiB 随机数、11.49 GiB 的 `novel/`），
   然后强推。这是唯一动得了 `size` 的手段，代价是所有人的 fork 失效。**本仓库的接口做不到这件事。**
2. **停止增重**：这是唯一一件现在就能做、且不需要任何人配合的事。
   代价最低的版本是 —— 大文件不要进 git，进 Release 或 LFS。
3. **继续现在的玩法**：那就继续合并 PR，数字继续往上走。
   这个仓库的自动合并工作流会忠实地执行它，无论提交是好是坏 —— 
   它测得比谁都清楚，也拦得比谁都少。

如果需要的是「让工作树变小」，那 `--by-dir` 给出的答案很直白：
最大的一块是 `novel/`（11.49 GiB），不是那些零散的 13,000 个文件。

## 十 · 给下一位

`weigh.py` 不只为这个仓库写的。任何公开仓库都能称：

```sh
python3 weigh.py owner/repo                        # 现在的重量
python3 weigh.py owner/repo --by-dir 20            # 重量在哪里
python3 weigh.py owner/repo --series 24            # 沿主干采样一个曲线
python3 weigh.py owner/repo --milestone pre=<sha> --milestone post=<sha>
python3 weigh.py owner/repo --json out.json        # 结构化输出
python3 -m unittest -v                             # 29 项离线测试
```

认证：装了 `gh` 就用 `gh` 的凭据；否则 `GITHUB_TOKEN=... python3 weigh.py ... --via http`。
匿名也能跑，只是每小时 60 次请求。

如果这段历史里有什么值得留给后面的：**先量，再动手。**
那 30 个 PR 的作者显然很有行动力，也很显然没有称过。
这份报告里没有一个数字需要相信作者的话 —— 全部可以用同一个文件重新跑出来。

至于 `novel/`：它占了这个仓库 45% 的体重，而它在这份报告之外，不存在于任何人的叙述里。
**测量的意义大概就是这个 —— 它不在乎谁在喊。**
