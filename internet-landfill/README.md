# 互联网垃圾填埋场

**这里堆着 32 件从真实互联网上捡回来的垃圾，附带一份它们的价格单。**

全部垃圾压缩后占 64,604 字节。这个仓库里最小的那 40 块随机砖，每一块是 104,857,600 字节。也就是说：**这次丢上去的全部东西加起来，是任意一块砖的 1/1623。**

这个数字不是修辞,是这次测量的结果,也是这份东西唯一的论点 —— **垃圾有两种价格,差三个数量级,而往这个仓库里丢垃圾的人从来只挑贵的那种。**

---

## 0. 这份东西是什么

三部分：

| 文件 | 作用 |
|---|---|
| `junk.py` | 采集器 + 度量器。`--fetch` 去互联网上捡，`--analyze` 给它称重 |
| `specimens/` | 32 件从真实互联网捡回来的标本，每件保留来源 URL 与抓取时刻 |
| `controls/` | 4 件自产对照，用来给「垃圾的价格」标定刻度 |
| `manifest.json` | 每件标本的完整度量：字节数、熵、三种压缩比、词汇贫乏度、脱敏记录 |
| `ledger.json` | 仓库侧的账本：25.45 GiB 里哪些压得掉、哪些压不掉 |

这不是一个安全工具。里面没有任何恶意样本、凭据或个人数据；捡回来的文本都过了脱敏，且每件都能凭 URL 复核。见 §7。

## 1. 采集偏差说明：从这台机器看到的互联网不是互联网

这一点必须先说，否则后面所有结论都会被误读。

采集在这台机器上进行，出网经过本机代理。结果：

| 源 | 现象 | 真实原因 |
|---|---|---|
| `cat-fact.herokuapp.com` | 无响应 | **确实死了**。Heroku 2022 年取消免费额度后该服务被拆 |
| `www.geocities.com` | HTTP 500 | **确实死了**。1994–2009，现存最著名的网络墓地 |
| `loripsum.net` | 无响应 | **无法判定**。可能死了，也可能只是本机看不见 |
| `www.wikipedia.org/robots.txt` | 代理 CONNECT 被拒 | **本机代理问题**，与目标无关 |
| `www.nytimes.com/ads.txt` | 连接超时 | **本机代理问题** |
| `www.google.com/robots.txt` | TLS 吊销检查失败 | **本机 schannel 问题**。加 `--ssl-no-revoke` 后正常拿到 6,587 字节 |

**结论：这次采集只能证明「从这一个观测点能看见什么」，不能证明任何站点的存活状态。** `dead-loripsum` 标本因此被明确标注为「无法判定」而非「已死」。一个只从单点观测的互联网考古，报出来的死亡率一定是虚高的 —— 这条规矩对上一轮的仓库称重同样成立。

补一句实操：`--ssl-no-revoke` 修好了整整一类失败。Windows 上的 curl 用 schannel，检查证书吊销状态时需要访问 CA 的 OCSP 服务器，在没有直连的环境里会整体失败。

## 2. 垃圾分类学

32 件标本，8 个类别。分类标准是「它为什么存在」。

| 分类 | 件数 | 原始字节 | 压缩后 | 压缩比 |
|---|---:|---:|---:|---:|
| 管道文件 | 9 | 139,827 | 27,449 | 0.1963 |
| 错误页 | 5 | 67,439 | 17,054 | 0.2529 |
| 填充文本 | 4 | 41,019 | 15,655 | 0.3817 |
| 占位数据 | 5 | 5,676 | 1,995 | 0.3515 |
| 无意义数据 | 4 | 2,659 | 1,503 | 0.5653 |
| 死链墓园 | 3 | 601 | 484 | 0.8053 |
| 样板文本 | 1 | 559 | 388 | 0.6941 |
| 企业黑话 | 1 | 58 | 76 | **1.3103** |
| **合计** | **32** | **257,838** | **64,604** | **0.2506** |

几个值得单独拎出来的标本：

- **`plumbing-ads-bing`（62,172 B，压缩比 0.1579）** —— Bing 的 `ads.txt`。每一行是一个广告转售授权记录，由不可读的发布商 ID 组成。它不是给人看的，它是给广告中间商之间互相取证用的。CNN 有 45,166 字节的同类文件，IMDb 20,245 字节，Spotify 只用了 1,273 字节 —— 整份收藏里最克制的一份，值得表扬。
- **`error-apple-404`（65,536 B，压缩比 0.2440）** —— Apple 没有 `ads.txt`。为了告诉你这件事，它传输了 **111,090 字节**的 HTML（超采集上限，标本截断至 64 KiB）。一次「没有」，成本 111 KB。
- **`error-httpbin-404` / `error-httpbin-503`（各 91 B）** —— 真正的零字节响应体。为传达同样的「没有」，它们用了 0 字节。和上一条放在一起看。
- **`plumbing-crossdomain-google`（235 B）** —— 一份为 Adobe Flash 写的跨域策略文件。Flash Player 于 2020-12-31 停止支持、2021-01-12 起拒绝播放内容。这份文件在 2026 年仍在正常伺服。**这是本次采集里唯一一个可以确认的、跨越了一次技术灭绝的僵尸。**
- **`plumbing-humans-google`（286 B）** —— `humans.txt`，一个「写给人类看的 robots.txt」、从未被广泛采用的约定。Google 留了一句话和一个招聘链接。32 件标本里唯一一件似乎在试图跟人说话的。
- **`noise-uuid`（33 B，压缩比 1.6061）** —— 一个 UUID。36 个字符，约 122 bit 实际熵，指向一个不存在的东西。

## 3. 怎么给垃圾定价

用了三个度量，各自只回答一个问题：

**熵（bits/byte）** —— 零阶字节熵 H = −Σ p log₂ p。它只数字节出现频率，**完全忽略字节之间的结构**，因此它是真实信息量的**上界**而不是答案。它的用途是分类，不是定价：H 接近 8.0 说明数据是扁平的（随机或加密），H 在 4–5.5 说明有结构。**不要用 H 去除以 8 去算「信息量」** —— 那会把一份压缩比 0.40 的网文说成比随机数「信息更多」。

**压缩比** —— `gzip.compress(data, level=9, mtime=0)` 后长度除以原始长度。这是**实测**，不是估算。这是定价的依据。同时报了 `lzma`（preset 9|EXTREME），代表现实中归档器能达到的下限。

**类型-记号比（TTR）** —— 去重词数除以总词数。衡量文本的词汇贫乏程度。企业黑话生成器的输出 TTR = 1.0：**每一个词都不重复，而整段话什么都没说。** 这是「高多样性 ≠ 高信息量」的一个袖珍证明。

## 4. 三条规律

### 规律一：垃圾越大越便宜

按体积排序后，压缩比单调下降：

| | 体积 | 压缩比 |
|---|---|---|
| `error-apple-404` | 65,536 B | 0.2440 |
| `plumbing-ads-bing` | 62,172 B | 0.1579 |
| `plumbing-ads-cnn` | 45,166 B | 0.2065 |
| `filler-lipsum-page` | 33,810 B | 0.3549 |
| … | | |
| `noise-uuid` | 33 B | 1.6061 |
| `corporate-bullshit` | 58 B | 1.3103 |
| `error-httpbin-404` | 91 B | 1.1209 |

原因不是玄学，是**固定开销**：gzip 的容器头加尾约 20 字节，与内容无关。

### 规律二：每个文件有一笔 20 字节的固定税

在 33 字节的 UUID 上，这 20 字节是 60% 的税 —— 压缩算法不但没赚，还亏了：`gzip(uuid) = 53 字节 > 33 字节`。

这条规律有一个真实后果：**一个仓库的垃圾成本，不只取决于总量，还取决于碎片数。** 同样的 100 KB，装成 1 个文件比装成 3,000 个文件便宜。

### 规律三：零信息有两种价格，差 996 倍

这是本次测量的核心。同样 1 MiB、同样信息量为零：

| 内容 | 原始 | 压缩后 | 比 |
|---|---:|---:|---:|
| 全是字母 `a` | 1,048,576 B | **1,052 B** | 0.001003 |
| 真随机字节 | 1,048,576 B | **1,048,628 B** | 1.00005 |

**差 996 倍。** 两者的信息量都是零：前者可以完全预测，后者完全不可预测 —— 但从「存储它要花多少钱」的角度，它们处在价格表的两端。

`noise-httpbin-bytes` 是这 32 件标本里唯一一件压缩算法完全无能为力的东西（实测 gzip 比 1.0225）。

## 5. 仓库侧的账本

上一轮已经量过：这个仓库的工作树是 **25.45 GiB**（27,324,768,617 B，576,161 个文件），而 GitHub 报的 `size` 是 **15.09 GiB** —— 差 5.3 倍。

这一轮多问了一个问题：**这 25.45 GiB 里，有多少是压得掉的？**

做法：对每个桶抽样抓取真实 blob，实测压缩比，再外推。没测到的桶给出区间而不是点估计。

| 桶 | 原始 | 占工作树 | 压缩比 | 依据 |
|---|---:|---:|---:|---|
| `novel/` 网文正文 | 12,339,600,452 | 45.16% | 0.3981 | 实测 14 个分层抽样 |
| **人工随机数据** | 4,194,304,000 | 15.35% | **1.00** | 40 个 100 MiB 文件，实测 |
| `rust-corpus/` | 3,196,891,972 | 11.70% | 0.2392 | 实测 14 个 |
| `dotnet/` | 2,794,954,720 | 10.23% | 0.2113 | 实测 14 个 |
| **已压缩媒体** | 1,955,141,037 | 7.16% | **1.00** | 扩展名普查：png 40.7% / mp4 39.4% / wav 13.7% / jpg 4.3% / mp3 1.8% |
| 未测的其余 188 项 | 2,843,854,913 | 10.41% | 0.25–1.00 | **外推，未抽样** |

**结论：25.45 GiB → 约 12.2–14.2 GiB，回收 44%–52%。**

### 关键的一行

压缩不掉的部分 = 随机数据 4,194,304,000 + 已压缩媒体 1,955,141,037 = **6,149,445,037 B（5.73 GiB）**。

- 它只占原始体积的 **22.5%**
- 却占压缩后体积的 **40%–47%**

**用 22.5% 的体积，支配了近一半的真实代价。** 这就是这份收藏想说的第二件事：在这个仓库里，重量和代价是两个不同的量。

### 一个反事实

如果只删掉那 40 个 100 MiB 随机文件：

- 原始体积：25.45 GiB → 21.54 GiB，**减少 15.35%**
- 压缩后体积：13.13→8.93 / 15.26→11.07 GiB，**减少 27%–32%**

**删掉 15% 的体积，换来压缩后减少三成。** 因为那 40 块砖根本压不动 —— 删掉它们，删掉的是纯成本。

（顺带一提，上一轮量到这正是 `Break-This-Repo/` 目录的构成：2,097,173,523 B / 23 个文件，其中 20 个恰好是 104,857,600 B。）

## 6. 结论

**这个仓库里最贵的垃圾，是 40 个 100 MiB 的随机块：声明 3.91 GiB，实付 3.91 GiB。**

**这次丢上去的是最便宜的那种：32 件真实互联网垃圾，声明 257,838 字节，实付 64,604 字节。**

两者信息量都是零。价格差三个数量级。

对任何想继续往这里堆东西的人，结论是可操作的：**堆文本是低效的。** 一个社区再怎么努力堆网文，一年的产出也抵不上一次 `dd if=/dev/urandom`。反过来说 —— 如果这个仓库哪天想瘦下来，它不需要删掉 45% 的 `novel/`，它只需要删掉 15% 的随机字节，效果更大。

以及最后一条，关于这件事本身：**丢垃圾可以几乎不花任何代价。** 在 25.45 GiB 的填埋场上加 64,604 字节，占工作树体积的 **0.00024%**。之前没有人这么丢过。

## 7. 复现

```bash
python junk.py --all          # 抓取 + 度量，重写 specimens/ controls/ manifest.json
python junk.py --self-test    # 16 项离线自检，不联网
python junk.py --only noise-uuid,plumbing-humans-google --fetch
```

只依赖标准库（`gzip` / `bz2` / `lzma` / `hashlib` 都不需要额外装），网络部分调用系统 `curl`。每个源只请求一次，间隔 0.4 秒。

仓库侧账本（`ledger.json` 里那些数字）用 `sample_repo.py` 复核，同样只读、同样不需要 clone：

```bash
python sample_repo.py ext  "琵琶曲" wallpapers "彼方的他Aliya"   # 扩展名字节普查
python sample_repo.py comp novel         --n 14                 # 分层抽样实测压缩比
python sample_repo.py comp rust-corpus   --n 14
python sample_repo.py comp dotnet        --n 14
```

`ext` 是那个便宜但关键的步骤：**先看清一个目录到底由什么格式构成，再决定用哪个压缩比去乘它。**
拿文本比 0.25 去乘一堆 PNG 会低估四倍。

体积总数由同仓库 `repo-scale/weigh.py` 产生（那也是这份收藏的上一轮）。
**没有下载任何一个 100 MiB 级文件** —— 上面关于那 40 块砖的每一个数字，都来自 API 返回的
`size` 元数据字段。

复现结果会与本文不同：`httpbin.org/uuid`、`catfact.ninja`、随机字节每次都会变。
标本里的 URL 和抓取时刻记录了当时的情况。

## 8. 边界

- **不含恶意样本。** 「垃圾」指公共填充文本、占位 API、错误页、爬虫与广告管道文件。没有任何可执行负载。
- **脱敏在写盘前完成。** 邮箱、电话、IPv4、32 字符以上的长 token 一律替换为 `[email-redacted]` 等标记，替换次数记录在 `manifest.json` 的 `scrubbed` 字段里。JSONPlaceholder 的假用户数据（含假邮箱与假电话）也照此处理。
- **每件标本保留来源 URL 与抓取时刻**，可逐件复核。
- **不做价值判断。** 分类按「它为什么存在」，不按「它好不好」。`plumbing-humans-google` 被收进来不是因为它是垃圾，是因为它是同类文件里唯一想跟人说话的一个。
- **单点观测的局限**见 §1。这份收藏反映的是 2026-09-22 从一台机器出发能看到的东西。
