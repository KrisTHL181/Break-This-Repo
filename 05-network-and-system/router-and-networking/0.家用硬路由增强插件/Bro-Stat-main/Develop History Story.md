## 十八、Tag 5：Bro-Stat 的“时空时代”

Tag 5 的名称是“多品牌时空算法、Canvas 优化修复新增提升,etc.”，并标记为 prerelease。“时空”在这一版有具体的源码含义，数据属于哪个时间，开始成为修改的重点。

以 ASUS 为例，旧代码先记录 `n = performance.now()`，再发请求；Tag 5 改为先 `fetch('/getTraffic.asp')`，等响应回来后再记录 `n = performance.now()`。旁边的注释写明：“WAN 与设备累计量来自同一个 getTraffic 响应。”

一行代码的位置变化，让时间记录从开始请求移到了响应抵达之后。它把计时点向实际的数据到达靠近，也使同一响应中的 WAN 与设备累计拥有相应的时间联系。积分的时间应当尽量跟数据本身绑定，这项原则在 Tag 5 中有了很直接的体现。

ZTE-Stat_Max X 在 Bro-Stat Tag 5 的前一天发布。X 的说明列出 WAN/LAN 独立时间戳、Group Time、设备离线尾部积分、AR 状态机优化，以及 8192 点 Canvas、RSSI 与 PHY。约二十四小时十九分钟以后，Bro-Stat 发布了“多品牌时空算法、Canvas”。

Tag 5 的文件差异也能找到对应变化：长度为 8192 的 `Float64Array`、Canvas 图表、设备消失时向零补齐的尾部积分，以及放到实际响应之后的数据时间。尾部积分的时长，还被限制在一个刷新周期内。

从正式成品史看，ZTE X 所代表的数据时间、离线边沿与固定长度波形记录，在相隔一天左右的发行中进入了 Bro-Stat 多品牌家族。第一行实验代码最早写在何处，可以继续做跨库考古；眼前的成品与时间，已经清楚记录了这两轮发布之间的联系。

## 二十、从共享代码，到迁移测量方法

早期移植中，UI、流量格式化函数与 HA Snapshot 都可以沿已有实现迁移。到了数据时间这一层，各厂商的读取方式开始直接影响计算安排。

ASUS 的 WAN 与设备累计来自同一个 `getTraffic.asp` 响应，可以共享相应的接收时刻；华为的 WAN 与 `/api/system/HostInfo` 分开读取，小米在 LuCI 环境中并发请求 `devicelist` 和 `status`，TP 使用自己的 DataStore POST，H3C 的部分信息则来自独立 ASP 页面。这些接口把数据以不同组合送到程序面前。

因此，迁移时间处理时，要先看数据在哪次响应中出现，再确定它的计时位置。可以共同遵循的原则是让时间尽量绑定真实数据源，具体做法则逐品牌安排。Bro-Stat 由此把复用推进了一层：一套测量方法，在不同后台中寻找各自恰当的实现。

## 二十一、Canvas：浏览器中的短时波形

Tag 5 让主要分支开始保存本地波形。ASUS 加入两个长度为 8192 的 `Float64Array`，并记录最大值、最小值、拖拽状态与待绘状态。这与 ZTE X 的 8192 点历史采用相近的设计，浏览器保存有限窗口内的近期变化，长期记录则交给 Snapshot 与 HA。

用户既能查看眼前的读数，也能沿曲线回看刚才发生的变化。Bro-Stat 的界面从仪表盘向示波器靠近，原本一帧帧掠过的速率，有了一段可以重新展开的波形。

## 二十二、5.5：各品牌开始按自己的节奏变化

Tag 5 发布不到二十四小时，正式 Release 5.5 随之出现。两者的名称都围绕多品牌时空算法、信号与 Canvas，文件变化却已显出差别：ASUS 增长约 5.7%，H3C 约 4.6%，Huawei 约 1.1%，小米成品大小完全相同，TP 只增加了两字节。

Tag 5 先把新一轮时间处理与图表能力送进各分支，5.5 随后依据不同品牌的实际情况继续完善无线信息和显示。这一轮修改的幅度开始各有不同，统一发布之中，已经能看见独立发展的节奏。

从后续历史回看，5.5 既是最后一次具有明显统一世代感的 Tag，也接在品牌分化逐渐清晰的位置上。共同的发行节奏暂时停在这里，各脚本自己的版本继续向前。

## 二十三、ASUS 5.5：RSSI 怎样进入用户的视野

ASUS 在 5.5 中加入 `2.4G信道` 与 `5.2|8G信道`，按实际信道分别用 `2407 + 5 * channel`、`5000 + 5 * channel` 换算频率，再通过 `20 * log10(f5 / f2.4)` 计算 RSSI 跨频段的视觉补偿。同时进入这一版的，还有 DOM 缓存、端口状态和 PHY Rate 等信息。

不同厂商如何提供 RSSI，是采集时需要解决的问题；取得 dBm 之后，界面如何表达频段差异，又需要相应的计算。ASUS 的这一处修改，让实际信道参与了信号显示，原始无线数据与用户眼前的图示因此多了一层具体联系。

## 二十四、5.5 之后：各品牌分别修改

截至本文考察的仓库状态，正式 Tag 停在 5.5，`5.5 → main` 还有三个提交。这一段可以称作“后 Tag 当代史”：全品牌的下一轮正式发行尚未出现，各厂商的修改已经先行进入主干。

作者开始更明确地依据具体后台行为分别调整。此前的共同能力仍在，各分支怎样取得数据、怎样处理失败，以及无线探测如何安排，则在后续提交中继续分化。这是本文所见 main 与发行时的 5.5 之间很重要的区别。

## 二十五、当代第一步：为读取失败保留恰当状态

九月初的小米和华为算法更新中，华为对失败响应的处理有一处重要变化。旧代码在 WAN API 失败时容易取得空值，空值又可能经过 `|| 0` 变成零；新代码先确认响应是否具有 `UpBandwidth` 与 `DownBandwidth`，只有合法响应才更新 `S.wInstUp / S.wInstDn`，其余情况保留上一份有效记录。

LAN HostInfo 采用相近的处理，解析失败时保留 `S.lastCI`。这一轮取得的数据是否有效，与设备是否离线，分别由对应条件判断。接口暂时失去响应，已有设备记录也就能够等待后续观测再更新。

这与后期 ZTE 的 Mesh 处理相通：没测到，不等于测到零。对累计与状态而言，`unknown` 和 `zero` 各有明确含义，读取失败需要作为观测缺失处理，才便于后面的统计继续使用这些数据。

## 二十六、小米：选择经过固件验证的 WAN 数据源

九月的一条提交说明写得很具体：“小米版结合实际固件情况，使用更精准的 WAN 数据源，避免回退到通用路径。”这一选择也体现出项目后期对数据口径的重视。

兼容处理中常见的做法，是一个接口失败后继续尝试其他路径，让程序尽可能取得结果。放在流量统计里，回退来源还需要满足相同的统计口径；返回一个数字只是开始，它代表哪些流量、来自怎样的统计过程，同样影响最终结果。

小米后期保留经过实际固件验证的专属 WAN 源，将回退路径的取舍落实到这些条件上。适配的目标也由此更加具体：选定能够正确解释的数据，再让它进入已有统计。

## 二十七、九月重构：“每个品牌单独适配”

随后的一次重要提交，标题直接写着“吸收并重写下游优化，重构，每个品牌单独适配”。其中降低了信道探测成本，移除冗余，采用小米专属 WAN 数据源，并修复 ASUS 的 HA 名称与数组问题。H3C 的特定型号状态和寄存器得到处理，TP 则依据社区经验调整合并与并行包请求。

这些修改分别落在厂商特有的细节中。共同的统计含义继续保留，各品牌如何读取、解释和组合数据，则按照实际后台重新安排。早期迁来的骨架经过数月使用，已经长出了各自需要的结构，“每个品牌单独适配”也终于写进了提交标题。

## 二十八、独立适配，把厂商的真实差别留在代码里

相似函数和设备数组，很容易让人想到提取公共代码。Bro-Stat 的各分支也确实有不少相近形态，但采集过程需要照顾的，是五群互不商量的黑盒厂商。

ASUS 通过 `/getTraffic.asp` 取得相关流量，还能独立读取 `/get_port_status.cgi`；Huawei 使用 `/api/ntwk/wan?type=active` 与 `/api/system/HostInfo`；Xiaomi 在 LuCI stok 环境下并发请求 `/api/misystem/devicelist` 和 `/api/misystem/status`。H3C 要解析 GBK 编码的旧 ASP 页面与 JavaScript 数组，TP 则构造自己的 DataStore 请求对象，本文所见版本还专门使用 `TP_COMBINED_REQUEST`，按后台能力合并 WAN 与在线终端查询。

这些差异直接关系到哪些数据同时返回，以及每份数据对应什么时间。公共接口即使采用相近的函数名，也需要把这样的关系表达完整。后期的独立适配，正是把各厂商的实际读取顺序与组合方式留在实现中，再让它们通向一致的统计含义。

## 二十九、Bro-Stat 共同遵循的规则

分支之间仍然有清楚的共同血统。流量按速率与实际时间计算，零速率起动、结束以及设备消失时的尾部需要分别处理。接口失败保留观测缺失的含义，官方累计、瞬时积分和 WAN 观测则可以相互参照，结合各自的来源与状态使用。

在时间和历史方面，积分尽量联系实际数据，短时波形使用固定长度内存，长期记录进入持久化或 HA。采集安排还要照顾后台负担，已经取得的数据尽量复用，读取方式则依据各厂商的能力选择。

这些规则贯穿各份脚本，构成了它们的共同联系。源码中仍有相似片段，也有不同的请求和处理顺序；从最终行为看，各分支都在努力让同一种读数具有可以对应的含义。

## 三十、history 里的四件化石

本文所见的 `history/` 留下四份文件：ASUS 改版、TP 5.9.0、华为后台频率测控探针，以及小米 5.9.3。Git 保存提交过程，history 则像一个小小的展柜，放着作者挑选出来、值得以后重新打开的代表稿。

这些文件各有自己的位置。有的留下某个品牌较早的形态，有的保存一条算法血统，华为探针则把实验方法也留在了正式成品旁边。用 Bro-Stat 测路由器之前，先用 Probe 看一看路由器提供给 Bro-Stat 的数据隔多久变化一次。测量工具旁边，还有一件用来研究它的数据来源的工具，这种“套娃”颇有作者的趣味。

## 三十一、社区史，也是一部“谁手里有什么硬件”的历史

早期 1-Reality 参与多品牌同步，H3C 的加入带着共同作者记录，相关发行提交又感谢提供真实测试环境的用户。到了九月重构，社区下游优化被吸收进来，共同作者也继续出现在记录中。

Bro-Stat 的协作有一个很实际的条件：谁家里有那台需要研究的路由器？运营商定制 H3C、某代华为固件、某种 TP DataStore、ASUS AiMesh 或小米 LuCI 分支，都可能提供作者手中设备无法呈现的情况。这些机器连同它们的实际响应，构成了适配所需的材料。

有时，重要的贡献就来自一位愿意让作者远程查看自家后台的用户。这种协作很接近硬件驱动的社区生态：设备怎样运行，异常怎样出现，都能补充纸面资料尚未说明的内容。某种意义上，设备就是文档，异常也在为程序补写规格。

## 三十二、文件体积里的同步与分化

Release 3 时，ASUS 约 54.2 kB，H3C 约 54.3 kB，Huawei 约 65.9 kB，Xiaomi 约 58.5 kB，TP 约 50.4 kB。到了 Release 4，五者分别来到 67.8、71.3、74.6、67.4 和 59.4 kB，配合时间、存档与导出等能力一起增长。

Tag 4→5 又出现了一轮共同增长：ASUS 约增加 12.3%，H3C 约 3.5%，Huawei 约 11.4%，Xiaomi 约 12.4%，TP 约 14.5%。到了 5→5.5，幅度开始明显不同，ASUS 约 5.7%，H3C 约 4.6%，Huawei 约 1.1%，Xiaomi 为零，TP 也接近零。

本文所见 main 中，根目录文件的体积分别约为 ASUS 80.6 kB、H3C 76.5 kB、Huawei 84.8 kB、Xiaomi 77.8 kB、TP 68.4 kB。各品牌后来增加了不同的处理，文件也沿着各自的需要继续变化。从早期一起增长，到后期各走各的节奏，这条曲线保留了整个家族逐渐分化的形状。

## 三十三、版本号也在记录“物种分化”

各分支的名称渐渐带出了各自的性格：华为到了 U，小米叫 Turbo，TP 叫 lab，ASUS 仍在 5.9.7，H3C 则为 5.9.5。这套命名离整齐划一很远，却留下了独立发展的痕迹。五份程序共享成果，也各自经历修改，内部版本便随着自己的进度向前。

仓库 Tag 负责标记整个家族整理到什么状态时发布，脚本内部版本则记录具体分支的演变。读懂这两层关系以后，那些看似凌乱的后缀便有了位置：同一次发行中，几个品牌可以处在各自不同的阶段。

## 三十四、提交标题之外，还要看源码发生了什么

本文考察的 head 提交，标题仍是“吸收并重写下游优化，重构，每个品牌单独适配”。打开实际补丁，修改却只落在 ASUS、H3C、小米三份文件的单位文字上，例如 `KB/s → KiB/s`，或某个分支中的 `KB/s → K/s`。真正大规模的逐品牌适配，发生在它前一个采用相近标题的提交中。

这处差别值得保留。标题是作者写给人的摘要，文件差异记录实际改动；研究版本演变时，两者应当相互参照。若只依据提交说明自动概括，九月六日那几行单位修改，就很容易被写成第二次架构革命。

那就属于考古事故了。源码比文档重要，diff 比 commit 标题重要，这项原则在这里又有了一个具体例子。

## 三十五、main：5.5 之后的当代实验线

截至本文考察时，最后正式 Release 仍为 5.5，main 已经继续经历华为与小米算法调整、失效响应处理、信道探测降耗和小米专用 WAN 数据源的选择。ASUS HA 修复、H3C 特定寄存器与状态修复、TP 组合请求实验，以及单位文字修改，也都已进入主干。

最后一次代码推送对应九月上旬的 head，这些变化尚未获得新的正式 Tag。因而，称它为“Post-5.5 main，当代实验线”，更能表达它与发行成品的关系：5.5 提供起点，后面的提交继续保存各厂商的实验与修改。

这和 ZTE 的字母时代颇有不同。ZTE 为连续实验体不断添加后缀，Bro-Stat 则让各分支自己的版本号继续生长，联邦 Tag 暂时停住了。两个项目的“版本政治”，也走出了各自的样子。

## 三十六、沿着六个时代回看

最早是共同祖池时代。Bro-Stat 仓库尚未诞生，ZTE-Stat_Max、Mi-Stat_Max 与此前实验已经把 5.9 系统计骨架逐步养成熟。到了北京时间六月十七日，仓库建立，Xiaomi、ASUS、TP 同时成为开国成员，首发 Release 又将 ZTE 纳入发行体系，联邦建国时代由此开始。

Release 1→3 可以看作现实适配时代。TP 离线问题先进入修改，H3C 与 Huawei 随后加入，Probe、MLO、GBK 和旧 ASP 把各后台的具体差异带到了代码里。Release 3→4 则进入平台同步时代，时间、存档、自动导出、HA 与长期记录成批迁到各品牌，发行时刻又与 ZTE U 紧紧相连。

接近四十八天后，Release 4→5 带来时空统一时代。数据时间、离线尾部积分、Canvas 和短时历史一起进入多品牌家族，与 ZTE X 的发行紧密呼应。5.5 以后，物种分化逐渐鲜明，共同原则仍在，数据获取、错误处理、无线探测、WAN 来源与请求策略则按厂商分别优化。

如果未来继续加入腾达、其他新华三或更多 TP 系设备，这种分别研究、共同度量的方式也能继续延伸。新品牌带着自己的后台进入家族，再使用同一套度量衡解释取得的数据。

## 三十七、六个品牌背后的通用性

六个品牌是这段历史走到眼前的结果，它同时呈现了一个有意思的命题：通用性不一定来自更多共享代码。早期 Bro-Stat 依靠复制成熟骨架迅速移植，后来则允许代码分开发展，让各分支适应具体厂商。

与此同时，设备在线怎样判定、数据何时有效、积分对应哪一帧，以及设备离线时如何结束最后一段面积，都继续遵循共同的统计要求。短期波形与长期记录各有用途，未知状态也有别于真实零值。理解这些关系以后，底层通过 JSON、ASP、GBK 页面、LuCI 或 DataStore 取得数据，都可以走向相互对应的结果。

Bro-Stat 的跨平台能力，便是在这些共同要求与不同实现之间逐渐形成的。每个分支保留了适合自己的读取方式，最终的读数仍能放在同一套口径下理解。

## 三十八、Bro-Stat 与 ZTE-Stat_Max：向深处走，也向远处走

ZTE-Stat_Max 的历史像研究一台发动机。从 v1 到 Y，作者始终围着同一个黑盒生态往深处钻，越来越熟悉它在清零、漫游和缓存之间的细微行为。

Bro-Stat 则像把这台发动机的热力学原理带去造汽车发动机、船机、发电机，乃至航空发动机。真正动手以后，燃料、传感器、控制器与工况都要分别考虑，共同的理论也需要在每一种条件下找到合适的实现。最后联系着它们的，是能量守恒这样的原则，零件尺寸则由实际用途决定。

因此，Bro-Stat 的历史更侧重横向迁移以后重新寻找共性。各份源码中保留的相似与差异，都应连同这种迁移过程来理解。一个后台曾经给出的异常，一种接口实际采用的时序，都可能解释某条分支为何长成今天的样子。

## 三十九、今天再打开 Bro-Stat

沿着这段历史看，Bro-Stat 可以被理解为一套跨厂商硬路由 Web 控制面的测量规范，加上若干独立实现。这套规范主要保存在代码行为里，各品牌围绕相近的问题工作，再依据自己的后台给出答案。

WAN 此刻的速率、设备与本次会话的累计，是页面上最直接的读数；它们背后还需要辨认计数增长、清零、回流与缓存，确认数据所属的时间，并判断设备消失来自离线还是读取失败。无线信号怎样显示，结果怎样保存并送往 HA，又把观测继续带到使用者面前。

不同品牌处理这些事情的办法各有特点，要回答的问题却逐渐稳定。顺着数据如何来到页面，再怎样进入历史记录读下去，这个家族的共同结构也就清楚了。

# 结语：走出家门以后

Bro-Stat 的第一天很有少年气。仓库刚建，十九分钟以后六千多行代码砸进来，不到四十分钟，Release 已经挂着四个 5.9.x 成品。它带着一个很自然的信念出发：既然我已经有这么好用的统计引擎，那就给每个品牌装一台。

TP 的离线修复很快带来了第一道难题，连“离线”都要按后台的实际行为重新理解。走到 H3C，2026 年照样有人给你 GBK ASP；华为的无线和 MLO 又有自己的世界。ASUS 的一份响应可以同时决定 WAN 与设备时间，小米则让人看到，错误的“通用回退”甚至不如没有回退。最初那副骨架，就在这些具体差别中逐渐长出了新的样子，项目也慢慢学会了一件更难的事：允许现实保持差异。

Tag 4 的时间、存档、导出可以全家共享，Tag 5 的数据时间与 Canvas 也一样。可到了 5.5 以后，华硕该怎么测华硕，小米该怎么测小米，H3C 那堆上古 ASP 就让 H3C 自己慢慢啃。各家有各家的办法，共同的读数仍然在同一套口径里。走了这么远，Bro-Stat 终于找到了真正应该统一的东西。

如果说 ZTE-Stat_Max 的故事，是一台仪器怎样越来越懂一台中兴路由器，那么 Bro-Stat 的故事，就是这套仪器走出家门以后，发现世界上根本没有所谓“路由器后台”这一种东西——有五六个完全不同的文明，都把自己叫路由器后台。

而 Bro-Stat 最终没有强迫它们讲同一种语言，只给它们发了同一套度量衡。
