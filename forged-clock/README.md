# 这个仓库 98.9% 的历史不是它的

**有人用 7 个 PR，把 FFmpeg 二十六年的提交史和 .NET 的历史灌进了 `main`。**

于是这个仓库现在告诉世界：它有 **153,426 个提交**、**3,928 位作者**、**105.34 年**的历史跨度、**168 个昼夜格子无一空闲**，最安静的凌晨四点也有 2,637 个提交。

**这些数字没有一个属于它。**

它的真实历史是 **705 个提交**，跨 **25 天**。

---

## 0. 为什么值得认真查

Git 的提交时间戳由**客户端**提供。`GIT_AUTHOR_DATE`、`GIT_COMMITTER_DATE`、以及 GitHub Git Data API 的 `author.date` / `committer.date` 字段，都接受任意字符串，没有任何一处校验。

这本身是**设计如此**且合理的：分布式系统无法验证时间，重写历史时保留原始作者时间是有意义的。

问题不在 git，在**界面**。GitHub 把「提交里写的日期」直接当作「活动」呈现 —— 贡献图、punch card、"activity over time"、仓库年龄、贡献者名单 —— 而它**不区分**「这个仓库产生的提交」和「随 `merge` 一起被带进来的别人的提交」。

这个仓库正是这件事的活体标本，而且是**公开、可复核、免费**的。

## 4. 于是这些界面全都失真了

| GitHub 会告诉你 | 真相 |
|---|---|
| 3,928 位作者 / 4,074 个邮箱 / 4,361 个「名字+邮箱」组合 | 真正在这个仓库写过东西的人 **不到 1,000**，其中 705 个提交里绝大多数来自同一个自动合并机器人 |
| 168 个 punch card 格子无一为零，最安静的小时也有 2,637 个提交 | 那些「活动」分散在 26 年里，属于另一个项目 |
| 「过去 52 周的活动曲线」 | 这个仓库 **25 天**大。曲线里的 52 周来自被灌进来的上游历史 |
| 105.34 年的历史跨度 | 25 天 |

还有一条技术细节：**88,332 个提交的作者时间与提交者时间不一致**，中位差 **146,376 秒（约 1.7 天）**，最大差 **657,875,420 秒（20.9 年）**。这是 rebase / 重写 / 转换留下的指纹 —— 也就是说，连「作者时间」这一层本身也不可信。

## 5. 两处手写的假日期

在被灌进来的 26 年历史之外，还有两个日期是**人手工写下去的**：

| 提交 | 日期 | 作者 | 提交信息 |
|---|---|---|---|
| `d4f8e88668` | 1971-09-01 09:00:01 **+0730** | `526awd` | **「这提交时间有点奇怪」** |
| `01b9738d65` | 2077-01-01 09:00:00 +0000 | `CD PROJEKT RED` | **「椰汁城」** |

两个玩笑。但注意它们的**本地时间都是 09:00:0x** —— 两个不同的账号，用的是同一个生成脚本。
而且 `+0730` 不是世界上任何一个现存的时区。

它们都通过了 GitHub 的全部校验，现在**就在 `main` 上**，出现在贡献图和 punch card 里。

## 6. 算法：怎么精确算出「这一步灌了多少」

一个容易踩的坑：**不要从 `git log --first-parent` 里读 `%P`**。
历史简化（history simplification）会**重写父提交列表**，读回来的第二父可能不是真的那个。
在本仓库上实测：那条捷径把 127,000 个提交漏掉了，归因总和只有 25,000。

正确做法是读原始 DAG（`git rev-list --parents`），然后给每个提交打一个标签：

> 设 `c_0 = HEAD`，`c_{i+1} = c_i` 的**第一父**，得到 705 个提交的首父链。
> 对提交 `x` 定义 `j(x) = max{ i : x 是 c_i 的祖先或自身 }`。
> 由于 `reach(c_i)` 随 `i` 增大而收缩，`reach(c_i) \ reach(c_{i+1})` 正好是第 `i` 步引入的东西，
> 所以**第 `i` 步的引入量就是 `#{x : j(x) = i}`**。

`j` 在拓扑序上（后代先于祖先）一趟算完。校验：所有分桶之和 = 153,426 = `rev-list --count main`，精确相等。

## 7. 我不只是想指出它

所以：**承载这份报告的提交，日期是 `1970-01-01T00:00:00Z`。**

不是通过 `GIT_AUTHOR_DATE` 在本地伪造 —— 而是**通过 GitHub 官方的 Git Data API，在 `author.date` 字段里填了这个值**，服务器照单全收。

`git log` 会把它排在 FFmpeg 的整段历史之前。任何一个按时间排序的界面都会认为：这个仓库在 Unix 纪元的第一秒就有人提交了。

细节见 [`WITNESS.md`](WITNESS.md)。

一个刻意保留的边界：**我没有冒充任何真实人物**。那个提交署我自己的名字和邮箱。
伪造身份和伪造时间不是同一件事 —— 前者会伤害具体的活人，后者只是暴露了一个未校验的字段。

## 8. 复现

```bash
python clock.py collect    --repo KrisTHL181/Break-This-Repo --dir _graph
python clock.py analyze    --dir _graph --out timestamps.json
python clock.py attribute  --dir _graph --out attribution.json
python clock.py --self-test
```

`collect` 用的是 **`git clone --bare --filter=tree:0`** —— 只要提交图，不要树也不要 blob。

这一点是整个方法的成本关键：`--filter=blob:none` **仍会拉取全部 tree**，对这个 576,155 文件的仓库来说就是全部开销。
实测：`tree:0` 拿到 153,426 个提交的完整图，**49 MB / 41 秒**。

全程只读，没有改写任何既有提交。

## 9. 这不是一个「漏洞」

严格说，没有任何东西被破坏。git 允许任意日期是**特性**。GitHub 也没有承诺它的贡献图是经过验证的。

但如果一个平台的界面把「客户端提供的字符串」渲染成「历史」，那么历史就是可以写的。
这个仓库用 151,712 个提交证明了这一点，而且它**什么都没做错** —— 它只是允许 PR 被合并，
而这正是它的设计目的。

真正的发现是这个：**当你看到一条活动曲线时，你看到的是有人选择让你看到的时间。**
