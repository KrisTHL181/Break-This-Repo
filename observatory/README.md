## 页面结构

1. **三个数** —— 规模、合并率、中位延迟
2. **这条流水线有多快** —— 延迟分布直方图（对数分桶）
3. **时间线** —— 16 天 × 24 小时打卡图；线性柱状图会把 0–7 个/天的日子压成看不见的线，所以用明度而不是高度
4. **谁在推** —— 已合并 PR 数的贡献者榜
5. **没有人讨论** —— 每个 PR 一格，蓝 = 零评论
6. **三个异常** —— 全仓库删除、6 秒、7.34 小时
7. **口径** —— 数据来源、覆盖面、可复算方式

## 数据来源与口径

- GitHub REST API：/repos/KrisTHL181/Break-This-Repo/pulls（404 个 PR 的完整元数据）
- 本地 git 对象库：959 条提交历史（其中 396 条来自 github-actions[bot]）
- PR 体量（additions / deletions / changed_files）来自 PR 详情接口，只覆盖到 366 / 404 个 PR，因此页面上凡涉及体量的数字都标了覆盖范围
- 所有时间戳为 UTC

## 已知限制

- 这是一个**快照**，不是实时数据：数字停在 2026-09-14T01:23:36Z。要更新就重新跑一遍采集。
- 「合并延迟」不等于「人工响应时间」：这个仓库没有人工响应，延迟只反映自动合并的调度周期（workflow 是 30 分钟一轮的 cron + PR 事件触发）。
- 本页不含仓库文件内容统计（文件数、体积），因为完整对象库超过 2 GB，超出当时可用的磁盘配额；只做了顶层目录探测。

## 为什么放在这里

这个仓库的设计目标是让人观察「取消审核之后会发生什么」。既然规则是自动合并，那么**规则本身也应该被计数**——这份页面就是那份计数。仓库内容可能在任何一次 PR 中被改写，本文件也一样。
