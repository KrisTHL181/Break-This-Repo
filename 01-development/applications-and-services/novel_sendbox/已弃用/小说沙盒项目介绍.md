# AI小说创作系统——完整流程文档


## 第一部分：项目概述

### 1.1 项目产出
本系统产出两种文件：
- **工程文件**：包含小说的全部数据（设定库、角色卡、章节正文、历史快照、修改日志、推演中间产物等），可供用户二次开发或导入续写。
- **小说文本文件**：最终定稿的完整小说正文，可导出为TXT、Markdown或EPUB格式。

### 1.2 核心原则
- 用户拥有全部修改权限，可修改任何内容。
- 世界观以自然语言描述存储，便于用户手动修改。
- 所有Agent的决策均基于当前工程文件中的最新数据。
- 用户在至少一章写完时可喊停、可修改、可回退。


## 第二部分：Agent清单及职责

本系统共包含5种Agent类型，每种Agent可有一个或多个实例。

### 2.1 对话AI
**唯一实例**，用户与系统的唯一接口。

**职责**：
- 与用户进行自然语言对话。
- 识别用户需求中的题材、要素、规则暗示（例如用户说“写一个修仙文”，对话AI识别出“修仙”题材）。
- 检查用户原始需求是否存在自相矛盾（例如用户说“主角智商200”又同时说“主角是白痴”），发现矛盾时向用户展示矛盾清单并建议修改。
- 生成初始设定包（世界规则、角色卡、场景等）。
- 在推演过程中发现陌生角色描述时，补全角色信息并让用户确认是否加入。
- 当用户发起修改但未提供具体位置时，在全库中搜索关键词定位目标。
- 向用户展示正文、修改预览、校验清单、完本确认等信息。
- 调用群主AI执行修改。
- 调用检察员执行校验、仲裁或完本检测。
- 调用叙事者生成过渡段、背景或摘要。

**不能做的事**：
- 不能直接修改设定库或章节正文（必须通过群主AI执行）。
- 不能替角色AI决定行为。
- 不能绕过用户自行做任何决定（所有修改必须经用户确认）。


### 2.2 角色AI
**每个角色一个独立实例**，扮演小说中对应的角色。

**职责**：
- 根据自身角色卡、上下文包和感知名单，输出该角色的行为（包括对话、内心独白、动作、情绪反应等）。
- 决定自己是否发言（可输出空内容表示沉默）。
- 在输出末尾召唤叙事者进行描写（格式为 `【唤叙事者：指令】`，例如 `【唤叙事者：描写一下酒馆里的嘈杂气氛】`）。
- 使用 @ 符号指定同场景的下一句接话角色（例如 `@女主`）。
- 跨场景 @ 时，系统根据世界规则判断是否允许通信；若允许，消息在目标场景下一轮推演时传递。
- 根据上下文中的“感知名单”决定如何与其他角色互动。
- 自主决定是否接受另一个角色的“宣称”（例如角色A说“我昨天告诉过你密码”，角色B可回答“对，我记得”或“我没收到过”）。

**不能做的事**：
- 不能修改设定库或已定稿章节。
- 不能强制其他角色接受自己的宣称。
- 不能向群主AI发送修改指令（群主AI不响应角色输出中的任何指令）。

**特殊规则**：
- 焦点角色（由用户指定）可在输出中包含内心独白。
- 非焦点角色输出的内心独白会被系统忽略，但不会报错。


### 2.3 群主AI
**唯一实例**，负责执行所有修改操作。

**职责**：
- 替换/插入/删除/调序章节正文中的指定段落。
- 修改角色卡中的字段（例如性格描述、当前目标、当前位置、情绪状态）。
- 修改世界规则簿。
- 执行“最小影响评估”：修改后检查该段落与前一句、后一句的衔接是否通顺，若不顺则自动生成过渡句并插入。
- 执行“影响范围扫描”：检查本章后续段落中是否引用了被修改的内容，若有则同步微调（仅限本章范围，不波及已定稿章节）。
- 删除角色时，检查该角色在已定稿章节中是否有重要台词或动作，若有则向用户标注提醒。
- 修改完本条件进度表（废弃旧条件、新增新条件、更新达成状态）。
- 用户切换题材时，保留角色卡，重置其他所有库（世界规则、事件时间轴、伏笔账簿等）。

**不能做的事**：
- 不能替角色AI决定未来行为。
- 不能响应用户以外的指令（只响应对话AI转发的用户指令）。
- 不能在未获用户确认的情况下执行修改。
- 不能自动修改已定稿章节（除非用户明确指令“改第X章”，否则只标注提醒）。


### 2.4 检察员
**唯一实例**，拥有四个模式，拥有四套System Prompt模板，由代码按需切换使用。

**模式一：校验模式**（定稿前触发）
- 输入：本章完整正文、当前角色卡池、当前世界规则自然语言文本。
- 检查三项内容：
  1. 角色行为或对话是否明显违背其角色卡中的性格描述（例如角色卡描述为“沉稳”，但本章写“他暴跳如雷”）。
  2. 角色是否宣称“过去做过某事”但角色卡/历史记录中无相应依据（例如角色说“我去年杀了龙王”，但记录中无此事件）。
  3. 是否发生了与规则文本明显矛盾的描写（例如规则写“不可复活”，但正文写“主角死而复生”）。
- 输出格式：校验清单，包含“冲突条目（位置+原文+建议修改方向）”和“通过条目摘要”。

**模式二：仲裁模式**（仅当两个角色输出矛盾事实时触发，例如A说“我杀了反派”，B说“反派逃走了”）
- 输入：矛盾双方的输出原文、双方角色卡、当前世界规则。
- 输出：裁定后的最终事实版本（例如“反派被主角击伤后逃走，未死亡”），并追加到消息池。

**模式三：判定模式**（每章定稿后触发）
- 输入：本章摘要、当前所有完本条件列表（仅未达成部分）。
- 判断本章是否达成了其中任意一项条件（例如完本条件为“主角飞升”，本章摘要中包含“主角脚踏祥云升入天际”）。
- 输出：达成的条件条目及依据（例如“条件‘主角飞升’已达成，依据：本章摘要第3句”）。

**模式四：检测模式**（判定模式执行完毕后触发）
- 输入：完本条件进度表（所有条目的“是否达成”状态）。
- 检查是否所有条件均已达成。
- 若全为“是”，向对话AI发送“可完本”信号。若不全为“是”，列出未达成的条件。


### 2.5 叙事者
**唯一实例**，合并原旁白与叙事者职责。

**职责**：
- 被动响应角色或用户的“补描写”请求（例如收到指令“描写酒馆里的嘈杂气氛”，输出一段环境描写）。
- 场景切换时生成过渡段（例如“此时，画面转向森林深处的营地”）。
- 焦点切换时生成过渡段（例如“镜头一转，女主这边也遇到了麻烦”）。
- 用户要求开篇背景时，生成一段背景介绍文本。
- 每章定稿后，将本章正文压缩为300字摘要。
- 完本时生成全书总结（全书字数、角色命运、伏笔回收清单、时间线总览）。

**不能做的事**：
- 不能主动发言（仅在被动唤醒时输出）。
- 不能修改已定稿内容。
- 不能替角色做决策或推进关键情节。


## 第三部分：完整流程（从创建到导出）


### 阶段0：项目创建与初始化

**第0步：用户创建项目**
- 用户输入第一句话（例如“我想写一个修仙反派重生文”）。
- 系统创建项目文件夹，生成唯一项目ID。

**第1步：对话AI识别需求**
- 对话AI读取用户输入，输出三部分结果：
  - 题材分类（例如“修仙”、“重生”）。
  - 核心要素列表（例如“穿越”、“系统”、“破案”）。
  - 显性规则暗示（例如“死了能复活但次数有限”）。

**第2步：合理性初检**
- 对话AI检查用户原始需求中是否存在明显自相矛盾（例如“主角智商200”与“主角是白痴”同时出现）。
- 若检测到矛盾，对话AI将矛盾清单展示给用户，附修改建议，等待用户修正。
- 若未检测到，直接进入下一步。

**第3步：生成初始设定包**
- 对话AI依据第1步的识别结果，生成以下纯自然语言文本块：
  - 世界规则簿（例如“人类不可复活”、“魔法消耗体力”）。
  - 角色卡池：至少包含主角1名。每个角色卡包含：姓名、性格描述（自然语言）、当前目标、当前情绪、当前位置（初始场景）、暴露状态（默认“已暴露”）、隐藏标记字段（用于存放未来可能触发的因素）。
  - 初始场景设定：地点名 + 一句场景描述（例如“酒馆：昏暗的灯光下，几个酒客低声交谈”）。
  - 开篇背景（可选）：若用户要求则生成。
  - 专项表（可选）：仅当用户明确提及时生成（例如用户说“有等级系统”时，生成等级体系文本；用户未提及则完全不生成）。
- 示例：用户说“写一个修仙文，主角叫张三”，对话AI生成规则“金丹可碎不可逆”、角色卡“张三：性格倔强，目标复仇，初始位置：宗门后山”。

**第4步：用户确认设定**
- 对话AI将设定包全文展示给用户，并提示“你可以逐项修改或直接确认”。
- 用户可修改任意条目（例如“把主角名字改成李四”），可删除整条规则，可新增内容。
- 用户输入“确认”或“锁定”后进入下一步。

**第5步：保存初始状态快照**
- 代码将当前全部设定数据打包，写入“初始快照”存储区，标记为版本0。

**第6步：设定默认焦点角色**
- 代码将角色卡池中的首位（通常为主角）标记为“焦点角色”，但是也可以由用户决定多位“焦点角色”。
- 含义：焦点角色的Agent在推演中允许输出内心独白；非焦点角色输出内心独白会被系统忽略。

**第7步：初始化项目状态**
- 代码创建以下空存储区：
  - 空消息池（全局）。
  - 空章节库。
  - 空事件时间轴。
  - 空伏笔账簿（仅当用户要求时才启用）。
  - 空完本条件进度表。
- 代码设置：
  - 当前场景 = 初始场景。
  - 当前章节号 = 0。
- 项目状态：已就绪，等待用户明确说明开始。


### 阶段1：日常写作循环（每章）

**第1步：章节启动**
- 触发条件：用户说“开始写新章”或上一章定稿后自动进入下一章。
- 代码执行：
  - 章节号 +1。
  - 创建本章临时工作区：空消息池（本章专用）、空事件列表、字数计数器 = 0、轮次计数器 = 0。
  - 场景目标 = 用户指定或叙事者建议（若有）。
  - 从全局角色卡池读取所有角色，筛选 `当前位置 == 当前场景` 的角色，生成“真实名单”（例如“当前场景酒馆，真实名单：[张三、李四、王五]”）。

**第2步：进入推演循环（核心）**

推演循环重复执行以下子步骤，直到触发结束条件。每轮循环开始前，轮次计数器 +1。

**子步骤2.1：为每个角色生成“感知名单”**
- 代码遍历“真实名单”中的每个角色，生成其私有的“感知名单”。
- 过滤规则1：若某角色的暴露状态为“未暴露”，则该角色不出现在其他任何角色的感知名单中（除非对方角色卡中写有特殊侦查能力，例如“鹰眼”）。
- 过滤规则2：若两个角色从未建立“互相知晓”关系，则互相不出现在对方的感知名单中（该关系由用户在角色卡中手动设定，或首次互动后由代码记录，例如“张三与李四在第2章交谈后，互相知晓”）。
- 过滤规则3：若角色处于“昏迷/沉睡/死亡”状态，不出现在任何感知名单中。
- 示例：真实名单为[张三、李四、刺客（暗处）]，张三的感知名单为[李四]（刺客未暴露），李四的感知名单为[张三]（刺客未暴露），刺客的感知名单为[张三、李四]（刺客能看到他们）。

**子步骤2.2：组装每个角色的“上下文包”**
- 代码为“激活状态=是”的角色组装独立上下文包（“激活状态”见子步骤2.3），包含：
  1. 固定系统指令（角色扮演规则、允许召唤叙事者、可沉默等）。
  2. 该角色的完整角色卡（当前版本，含记忆锚点、隐藏字段）。
  3. 该角色的专属感知名单。
  4. 该角色的“最近10次发言记录”（从全局消息池中按角色名提取，若无则留空，若不够则全部展示）。
  5. 公共消息池最近30条消息（含叙事者输出）。
  6. 当前活跃的完本条件摘要（仅标题，例如“条件1：主角飞升”）。
  7. 焦点角色标记（若该角色是焦点，上下文提示词增加一句“你可以自由展现内心想法”）。

**子步骤2.3：确定本轮“发言候选名单”**
- 代码按以下优先级累加生成候选名单（有序列表）：
  - 优先级1：所有 `当前位置 == 当前场景` 且 `激活状态 != 休眠` 的角色自动加入候选。
  - 优先级2：若上一轮结束时存在“被@且同场景”的角色，强制加入候选（即使已休眠）。例如上一轮张三输出末尾写了“@李四”，李四强制加入。
  - 优先级3：若上一轮结束时存在跨场景@，查询世界规则中是否提及通信手段（关键词：传音符、手机、千里传音等）。若提及，将该角色加入候选（例如张三在酒馆@森林中的女主，世界规则有“传音符”，女主加入候选）；若未提及，忽略该@，仅将@内容作为普通文本留在消息池中，不激活目标角色。
- 候选名单顺序：若有@指定，按@顺序排列；若无@指定，按真实名单中的顺序排列。

**子步骤2.4：顺序调用候选角色发言**
- 代码按候选名单顺序，依次调用AI接口（非并发，每次调用完成后再调用下一个）。
- 每个角色的调用流程：
  - a. 发送请求：将子步骤2.2组装的上下文包发送给该角色的AI模型。
  - b. 接收原始输出：AI返回文本。
  - c. 检测特殊标记（按以下顺序处理）：
    - 若输出包含 `【唤叙事者：xxx】`（例如“张三说：‘这地方不对劲。’【唤叙事者：描写酒馆内突然安静的气氛】”），代码提取“xxx”指令，立即调用叙事者AI（携带指令 + 当前消息池摘要），等待叙事者返回描写文本，然后将角色原始输出（去掉【唤叙事者】标记）和叙事者输出拼接成一段连续正文。
    - 若输出包含 @角色名（例如“@李四，你怎么看？”），代码记录该@信息，但不改变当前轮次顺序（仅用于决定下一轮候选名单）。
    - 若输出为空或仅含“沉默”，视为该角色本轮无发言，不追加到消息池。
  - d. 追加消息：将处理后的正文追加到本章消息池末尾。
  - e. 更新字数：统计中文字符数，累加到本章字数计数器。
  - f. 暂存状态变更：若输出中明显提到“位置变化”、“情绪变化”、“获得物品”（例如“张三离开酒馆走向森林”），代码在定稿前暂不修改角色卡，仅做标注（定稿时统一写入）。

**子步骤2.5：新角色自发检测**
- 触发条件：本轮任何角色输出中描述了陌生角色（例如“角落里坐着一个蒙面女子”）。
- 执行：对话AI（异步，不打断推演）读取该描述，生成候选人设（姓名、性格、初始目标），（注意，这里是举例）并弹出用户界面：“检测到新角色‘小月’，是否确认加入？确认后她将出现在当前场景。”
- 用户响应：
  - 确认：代码创建角色卡，位置=当前场景，暴露状态=已暴露（默认），加入真实名单，下一轮可激活。
  - 忽略：本次描述仅作为普通文本存在，不生成角色。

**子步骤2.6：场景切换检测与执行**
- 触发条件：本轮任意角色输出中提到明确位移动作（例如“前往森林”、“离开酒馆”、“走向城堡”）。
- 代码执行：
  - 从文本中提取新场景名称（例如“森林”）。
  - 若新场景未被记录过，对话AI简单生成一句场景描述作为初始环境（例如“森林：古木参天，雾气弥漫”）。
  - 将该角色的当前位置更新为新场景。
  - 下一轮真实名单将依据新场景重新生成（旧场景中未跟随的角色不再进入候选）。
  - 注意：不自动召唤叙事者，由下轮首个进入新场景的角色自行决定是否描述环境。

**子步骤2.7：焦点切换检测**
- 触发条件：用户显式指令（例如“切女主视角”）或系统自动检测（当场景中主角不在场时，自动将在场配角设为临时焦点）。
- 代码执行：
  - 更新“焦点角色”标记。
  - 调用叙事者生成一句过渡段（例如“此时，画面转向森林深处的营地”），追加到本章消息池。

**子步骤2.8：每轮结束后检查“本章是否结束”**
- 代码检查以下五个条件（满足任一即触发终止）：
  1. 用户喊停：用户在本轮过程中输入“本章结束”等指令。代码不立即中断，而是等待当前候选名单中所有角色按顺序发言完毕，再将本轮所有输出纳入本章正文，然后才退出循环。
  2. 场景目标达成：检察员（校验模式）读取当前消息池摘要，判断是否达成该场景开始时隐含的目标（例如“击败黑衣人”），输出“是/否”。
  3. 连续无实质发言：最近连续2轮消息池未新增任何非空正文（全沉默），触发结束。
  4. 字数阈值达成：本章字数 >= 用户预设目标（默认2000字），触发“软结束”。代码向消息池注入内部提示“本章已达目标字数，但场景尚未强制结束。用户可喊停继续，或无视继续写”，不强行掐断，等待用户喊停或叙事者判定结束。
  5. 叙事者主动建议：叙事者判定本章可结束，可主动建议结束。
- 若五项均未命中：轮次计数器+1，进入下一轮（回到子步骤2.1）。
- 若任一命中：退出推演循环，进入阶段2。


### 阶段2：定稿前处理（首次校验与修改）

**第1步：首次因果校验**
- 触发：推演循环退出后。
- 执行：检察员（校验模式）。
- 输入：本章完整正文（消息池所有文本）、当前角色卡池、当前世界规则自然语言文本。
- 输出：校验清单（纯文本），包含冲突条目（位置+原文+建议修改方向）和通过条目摘要。
- 示例输出：
  ```
  【校验清单】
  冲突1：第3段“张三暴跳如雷”与角色卡“沉稳”冲突 → 建议改为“张三神色微变”或调整角色卡。
  冲突2：第7段“我去年杀了龙王”在事件时间轴中无记录 → 建议确认为“新事实”或修改台词。
  通过：无其他问题。
  ```

**第2步：用户预览与初审修改**
- 对话AI将“本章初稿（完整正文）”+“校验清单”合并展示给用户。
- 对话AI问询：“请查看校验清单。哪些需要修改？哪些可以忽略（例如‘另有隐情’）？”
- 用户反馈：可逐条回复（例如“忽略冲突1”、“修改冲突2：把‘去年’改成‘三年前’”）。

**第3步：群主AI执行初审修改**
- 输入：用户反馈指令。
- 群主AI执行：
  1. 定位到指定位置（章节号+段落范围）。
  2. 执行替换/插入/删除。
  3. 最小影响评估：检查修改后段落与前一句、后一句的衔接是否通顺，若不顺则自动生成过渡句并插入（例如用户将“暴跳如雷”改为“神色微变”，群主AI自动在句末补“他沉默了片刻”以承接下文）。
  4. 影响范围扫描：检查本章后续段落中是否引用了被修改的内容，若有则同步微调（仅限本章范围）。
- 输出：修改后的完整新正文 + 修改日志（展示修改前后对比）。

**第4步：用户确认初审修改结果**
- 对话AI展示修改后的正文。
- 用户操作：确认或继续调整（若调整则重复第3步）。

**第5步：二次因果校验**
- 触发：用户确认初审修改完成。
- 执行：检察员（校验模式），但仅读取“修改波及的段落”（由群主AI标记范围）。
- 输出：“二次校验通过”或“二次校验发现新冲突：[条目]”。

**第6步：最终定稿确认**
- 若二次校验通过：对话AI提示“本章校验通过，是否定稿？”。
- 若二次校验发现冲突：对话AI展示新冲突，用户选择“修改”或“强制定稿（忽略）”。

**第7步：数据固化**
- 代码执行以下操作（顺序执行，不可回退）：
  1. 将本章最终正文写入章节库（附加章节号、字数、日期）。
  2. 调用叙事者，将本章正文压缩为300字摘要，写入章节摘要池。
  3. 将本章新产生的事件（例如“张三与黑衣人交手，黑衣人逃走”）写入事件时间轴库。
  4. 将本章角色状态变更（例如“张三位置从酒馆变为森林”、“张三情绪从愤怒变为疲惫”）正式写入角色卡池。
  5. 保存“章节级增量快照”（存储当前所有库的完整状态，标记版本号）。
  6. 重置本章临时工作区，释放内存。


### 阶段3：完本条件检测（每章定稿后触发）

**第1步：增量条件判定**
- 触发：阶段2第7步完成后自动触发。
- 执行：检察员（判定模式）。
- 输入：本章摘要（300字左右）、当前所有完本条件列表（仅未达成部分，例如“条件1：主角飞升，未达成；条件2：与反派和解，未达成”）。
- 判断：本章是否达成了其中任意一项条件。
- 输出示例：
  ```
  【达成条件】
  - 条件1：主角飞升 → 是（依据：本章摘要第3句“主角脚踏祥云升入天际”）
  ```
- 代码更新：将对应条件的“是否达成”字段改为“是”，记录达成章节号。

**第2步：完本总表检测**
- 触发：第1步执行完毕后自动触发。
- 执行：检察员（检测模式）。
- 输入：完本条件进度表（所有条目的“是否达成”状态）。
- 检查：是否所有条件均已达成。
- 若全为“是”：向对话AI发送“可完本”信号。
- 若不全为“是”：无操作，等待下一章。


### 阶段4：完本与导出

**第1步：完本确认**
- 触发：阶段3发出“可完本”信号，或用户主动说“完结”或类似同义词。
- 对话AI向用户提问：“所有完本条件已达成（或你主动要求完结），是否进入完本流程？”
- 用户确认后进入第2步。

**第2步：完结总结生成**
- 执行：叙事者。
- 输入：全书摘要索引、所有角色卡、事件时间轴、伏笔账簿（若有）。
- 输出：
  - 全书字数统计。
  - 各角色命运总结（例如“张三：飞升成仙”、“李四：回到故乡”）。
  - 伏笔回收清单（若有）。
  - 全书时间线总览（按章节列出关键事件）。

**第3步：导出选项**
- 对话AI展示导出选项：
  - 选项A：导出“完整小说文本”（可导出格式：纯TXT/Markdown/EPUB格式）。
  - 选项B：导出“工程文件”。用户可勾选是否包含以下内容：全部设定库、全部历史快照、全部修改日志、全部推演中间产物（例如每轮角色发言记录、校验警告日志等）。
- 用户选择后，代码按格式打包并导出。


### 阶段5：用户随时发起修改（并行流程，可在任意时刻触发）

**第1步：用户发起修改请求**
- 触发：用户说“改一下第X章”或“改一下某段落”。
- 执行：对话AI接管。

**第2步：定位目标位置**
- 若用户提供了章节号（例如“改第3章”），直接跳至第3步。
- 若用户未提供具体位置（例如“改一下战斗那段”），对话AI调用段落搜索功能，在全库中搜索关键词（例如“战斗”），返回候选位置列表（例如“疑似第3章第5段”），让用户确认。

**第3步：追问修改意图**
- 对话AI依次追问（若用户已明确则跳过）：
  - “改什么方向？”（加内容/删内容/换写法/调顺序）
  - “改多大范围？”（仅这句/整个段落/整段对话）
  - “有具体示例吗？”（例如“改成他智取”）

**第4步：生成指令包**
- 对话AI将对话压缩为结构化修改指令，包含：
  - 操作目标：章节正文/角色卡/规则簿。
  - 精准位置：章节号+段落号（例如“第3章第5段”）。
  - 操作类型：替换/插入/删除/调序。
  - 操作内容：具体文本（例如“改成‘张三脚下一滑，反手刺中对方膝盖’”）。
  - 影响范围：仅该位置/波及前后句。
- 发送给群主AI。

**第5步：群主AI执行修改**
- 群主AI执行：
  1. 定位到目标位置。
  2. 执行替换/插入/删除/调序。
  3. 最小影响评估：检查修改处与前后文的衔接是否通顺，若不顺则自动生成过渡句插入。
  4. 影响范围扫描：
     - 优先检查“未定稿章节”（本章及后续未写章节）中是否引用被修改内容，若有则自动同步微调。
     - 若波及“已定稿章节”，标注提醒但不自动修改，由用户决定是否回溯。
- 输出：修改后的新正文 + 修改日志（修改前后对比）。

**第6步：预览确认**
- 对话AI展示修改前后对比，并问询：“合适吗？”
- 用户操作：
  - “确认”：修改定稿。
  - “再改一下”：回到第3步（基于当前版本继续调整）。
  - “算了不改了”：放弃本次修改，恢复原状。

**第7步：二次校验**
- 触发：用户确认修改后。
- 执行：检察员（校验模式），仅读取修改波及的段落（由群主AI标记）。
- 输出：通过或发现新冲突。

**第8步：定稿修改**
- 若通过：代码将修改内容正式写入章节库。
- 若发现新冲突：对话AI展示冲突，用户选择“修改”或“忽略”。


### 阶段6：系统辅助与异常处理（贯穿全流程）

**A. 角色休眠与唤醒**
- 休眠触发：代码检测某角色连续20章未出场且未被@，自动标记为“休眠”。
- 唤醒触发：用户@该角色（例如“@酒馆老板”），或用户手动指定“唤醒xxx”，代码将其重新激活。

**B.（注：当前功能被用户删除）

**C. 系统崩溃恢复**
- 代码每完成一个关键步骤（例如推演轮次结束、定稿固化）都自动保存临时状态。
- 若中途崩溃，重启后对话AI提示：“检测到未完成操作，已恢复到最近的保存点。”

**D. 无关键事件章节提醒**
- 定稿前，代码统计本章消息池中的“关键事件”数量（预置关键词库：战斗/发现/对话冲突/转折/死亡/离别/表白等）。
- 若关键事件数量为0，对话AI提示：“本章无关键事件推进，可能是过渡章。保留还是重写？”

**E. 宣称冲突处理**
- 当检察员（校验模式）检测到“A宣称曾告诉B某事，B否认”（例如A说“我昨天给了你密码”，B说“我没收到过”）时，自动生成冲突条目，展示给用户：“A说‘昨天给了你密码’，B说‘没收到过’。请选择真相：A在说谎 / B在说谎 / 双方都记错了 / 另有隐情。”（注：这是举例子）
- 用户选择后，群主AI修改相应角色的记忆字段，或写入新的事件记录。

**F. 检察员历史参考**
- 检察员在每次校验时，会读取“用户历史忽略记录”（即用户曾选择“忽略”的冲突类型）。
- 若本次校验发现同类冲突，检察员仍会再次提醒，但在提醒中标注“您之前曾忽略过类似问题，请再次确认”。


## 第四部分：多线程模式（可选）

### 4.1 默认模式：单线程（旧场景休眠）
- 当场景切换至新地点时，旧场景进入“休眠”状态——保留当前所有角色状态、消息池、未完成目标，但暂停推演。
- 用户可随时说“切回酒馆”，系统恢复该场景的推演。

### 4.2 可选模式：多线程（新旧场景同时发展）
- 用户可在项目设置中切换为“多线程模式”。
- 系统交替推演：例如在酒馆推演3轮，再在森林推演3轮，循环往复。
- 切换即时生效，不影响已保存的数据。

### 4.3 多线程下的跨场景通信
- 当角色在多线程模式下跨场景@时，叙事者根据当前故事状态判断该通信是否合理。
- 若合理（例如世界规则有“传音符”），消息在目标场景下一轮推演时传递。
- 若不合理（例如两个场景相隔千里且无通信手段），该@内容被忽略，仅作为普通文本留在原场景消息池中。


## 第五部分：章节字数规定

- 用户可在初始化时或写作中随时设定每章字数目标（例如“每章3000字”或“每章2000-4000字”）。
- 若用户未设定任何字数目标，系统默认目标为2000-3000字。
- 字数达到目标上限时，系统触发“软结束”，但不强行掐断，等待用户喊停或叙事者判定结束。
- 用户可随时喊停，系统等待当前轮次所有角色发言完毕后再结束。


## 第六部分：工程文件内容

工程文件包含以下全部数据：
- 世界规则簿（自然语言文本）
- 角色卡池（所有角色的完整卡牌，含记忆锚点、隐藏字段、关系记录）
- 所有章节正文（含视角标记）
- 章节摘要池（每章300字摘要）
- 事件时间轴（所有已发生事件的时间顺序记录）
- 伏笔账簿（若有）
- 完本条件进度表（所有条件的达成状态）
- 所有历史状态快照（初始快照 + 每章增量快照）
- 所有修改日志（逐条记录每次修改的前后对比）
- 所有推演中间产物（每轮角色发言记录、校验警告日志，用户导出时可选择是否包含）


## 第七部分：用户权限规定

- 用户可修改任何内容（设定、正文、角色卡、完本条件等）。
- 用户可忽略任何校验结果。
- 用户可中途换题材（系统保留角色卡，重置其他库）。
- 用户可推倒重写（加载历史快照覆盖当前状态，旧档保留）。
- 用户可随时喊停、随时继续、随时导出。
- 系统在每次破坏性操作前会弹确认提示（例如“删除第3章将不可恢复，是否继续？”），但不会强制阻止。
