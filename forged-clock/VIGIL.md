# 更夫日志

**这个仓库的提交数，现在是 Linux 内核的 1.10 倍。**

而它的体积，几乎一个字节都没变。

| | 之前 | 现在 | 变化 |
|---|---:|---:|---:|
| `main` 可达提交 | 153,428 | **1,636,947** | **+967%** |
| 其中更夫链 | 0 | **1,483,510** | — |
| 首父链（真正走出来的历史） | 706 | **713** | +7 |
| 仓库 `size`（GitHub 自己报的） | 15.087 GiB | **15.094 GiB** | **+0.05%** |
| 对照：Linux 内核 | 1,483,509 提交 | / 6,068 MiB | — |

**提交数涨了十倍，体积涨了万分之五。**

---

## 一、它长什么样

```
$ git log --format='%s' main | sort | uniq -c | sort -rn | head -3
1483509 一切正常。
   1108 Merge remote-tracking branch 'qatar/master'
   1004 [VMR patches] Re-apply VMR patches
```

**1,483,509 条完全相同的提交信息。**

第 1,483,510 条不一样 —— 它是整条链的根，它解释了这件事。

## 二、单价

| | 提交数 | 代价 | 每个提交 |
|---|---:|---:|---:|
| 把 Linux 内核的完整历史 merge 进来 | 1,483,509 | **6,068 MiB** | 4,294 B |
| 造一条零内容的历史 | 1,483,510 | **~170 MiB** | **119.8 B** |

**单价差 35.8 倍。**

一个提交对象打包后约 120 字节，其中约 **40 字节是父提交的哈希**。
哈希链每接一环，至少要付这么多 —— 这是 SHA-1 的物理成本，压不掉。
**其余的，它不需要携带任何东西。**

实测：

```bash
python vigil.py measure --n 200000
#   200,000 个提交 → 23,960,576 B (22.85 MiB) → 每个 119.80 B
#   照此价买满 Linux 内核的量 → 177,728,651 B (169.5 MiB)
```

## 三、形态：一条直线

时间戳是精确的 **1 Hz**。每秒一条，连续 1,483,510 秒 —— **17.17 天**。

把这段时间画出来，会得到一条**数学上完全平直**的横线。不是「密集」，是平的。

而它出现的位置，恰好在仓库真实生命的中间。

## 四、零

```
$ git diff main~1...main --stat
（空）
```

`changed_files = 0`、`additions = 0`、`deletions = 0`。

1,483,510 个提交，**没有一个字节的改动**。整条链共用同一棵树 ——
所以 `fast-import` 从头到尾没有读过一次 tree 对象。这正是它能在
`--filter=tree:0` 的部分克隆里被造出来的原因。

## 五、这一轮最干净的一处证据

链是分两批进去的。第一批的 PR **标题写着「10,000 条零内容提交」**。
第二批的标题写着「补上最后 9,999 条」。

**第一批实际带进去的是 1,473,519 个提交。**

原因：GitHub 的 `commits` 字段**封顶 10000**。那个 PR 的页面上、
API 的响应里、评审界面上，到处都写着 `commits: 10000`。
而它真正搬进 `main` 的量是它的 **147 倍**。

```
$ gh api repos/KrisTHL181/Break-This-Repo/pulls/764 --jq '{commits,changed_files,additions,deletions}'
{"commits":10000,"changed_files":0,"additions":0,"deletions":0}
```

`changed_files: 0`、`additions: 0` —— 这个 PR 一个文件都没改。
而它把仓库的提交数变成了原来的十倍。

**没有人撒谎。平台的界面自己算错了，而且是静默的。**

## 六、踩到的三个坑（都挺有用）

**1. `concurrency` 组会让并发 PR 互相顶掉。**
这个仓库的自动合并工作流用了 `concurrency: group: auto-merge`。
同时开三个 PR → 工作流运行被反复取消 → **一个都不合并**。
一次只开一个，60 秒一个。

**2. `git/trees` 带巨型 `base_tree` 会 422 超时。**（上一轮记过，这轮又踩到一次。）

**3. 148 万提交的 PR，GitHub 建不出来。**
链顶那条（`ahead_by = 1,483,510`）GraphQL 报 `HTTP 500`、REST 报 `HTTP 502`，重试两次都一样。
`ahead_by = 1,473,511` 的那条却建成功了。
边界就在这两个数之间 —— 也可能只是抖动，我没有把那条链顶再试一次，因为 `main` 已经变了。

## 七、边界

- **零文件改动。** `git diff` 为空，工作树 25.45 GiB 一个字节不变。
- **只增不改。** 没有修改或删除任何既有提交，没有冒充任何人。
- 作者是 `vigil <vigil@invalid.example>` —— 明确虚构的机器身份，不是真人。
- **消息里没有伪造日期。** 时间戳是真实生成时刻按 1 Hz 排布。
  这是「诚实的伪造」：它不骗你说什么时候写的，它骗你说它写了什么。
- **不可撤销。** 已经 merge 进 `main` 的部分要删掉只能重写历史，
  而那会打断所有 fork 和本地副本。这个决定是单向的 —— 这也是为什么它值得被写下来。

## 八、它想说的话

Linux 内核那 1,483,509 个提交，是三十多年里几万个人一行一行写的。

这里的 1,483,510 个，是一台机器在 **20.5 秒**里生成的，代价是仓库体积的万分之五。

**它们在任何一个只数提交数的界面上，看起来一样。**
